# 案例：猫扑小说（rrssk 合作站 → 书源，签名 + 动态密钥 API 型）

> 站点：https://www.mopbook.com （小说站，GoEdge WAF + rrssk.com 搜索站）
> 成品：`猫扑小说.json`（同目录，v16）
> 技术要点首次沉淀于 `../js-api.md`（java.ajax 对比、POST 编码、ConsString、Mock DOM、动态密钥、分页去重）与 `../rules-spec.md`（两段式规则）。

## 站点特征

- **搜索经第三方站**：站内搜索走 `rrssk.com`（合作搜索站），需要执行签名 JS（`_t` token + `signJs` 环境指纹 + POST）。
- **目录 API 加密**：`POST /index.php?action=loadChapterPage`，body `data=AES-CBC-PKCS7(JSON{id,page})`；
  **密钥/IV 每日轮换**，藏在详情页引用的 32 位随机名 JS（如 `/templates/js/7M1GcU9Yk1yJcTNE3AEOsIIGEj5DnmN.js`）里。
- **WAF**：GoEdge，桌面 UA 与移动 UA 行为不同；机房/代理 IP 会被封（用户手机访问无验证码）。
- 详情页 meta `og:novel:*` 系列齐全；正文 `.content font18` 内 `<p>` 明文；同章分页 `/book/ID-N-2.html`。
- 每页都带一个**纠错举报表单**（`<div class="captcha">` + `<img src="/captcha.html">`）——导致 validator toc 阶段误报（见下）。

## 最终架构（v16）

| 链路 | 方案 |
|------|------|
| header | Android Chrome UA（过 GoEdge WAF） |
| searchUrl | `@js:` 三步链：00PB.html 拿 `_t`+signJs 地址 → Mock DOM 执行签名 → POST → 提取 q token 拼结果 URL |
| ruleSearch.bookUrl | **两段式** `onclick\n@js:`：jsoup 提取属性（自动解码 `&amp;`）→ base64 解码出详情页 URL |
| ruleBookInfo | meta og:novel:* 静态 CSS 选择器 |
| ruleToc.chapterList | `@js:`：动态提取密钥/IV（随机名 JS 正则）→ AES 加密分页请求 → **按 URL 去重** → 失败兜底 direList（**按章号排序**） |
| ruleContent | `.content@html` + `nextContentUrl: text.下一页@href` |
| exploreUrl | 37 条目（频道 3 列 0.29 / 分类 2 列 0.45 / 排行榜通栏） |

## 迭代史（每个坑都是通用教训）

1. **ConsString 报错**（v12→v13）：`java.ajax` 传拼接字符串 → `ConsString cannot be cast to String`。
   → 全部跨语言字符串用 `S()`（数组 join）拍平。
2. **WAF 挑战**（v13）：`java.post` 无书源 UA 裸奔被 GoEdge 挑战。
   → 全部改 `java.ajax`（自动注入书源 UA + CookieJar + 重定向）。
3. **搜索跳到 page=2**（v14）：结果页第一个 find 链接是"下一页"。
   → 提取 q token 自己拼 page 参数，不盲取页面链接。
4. **bookUrl 空**（v14）：`String(result)` 是 outerHTML，`&t=` 被转义成 `&amp;t=`。
   → **两段式规则** `onclick\n@js:`，让 jsoup 属性提取自动解码实体。
5. **目录 API 全失败走兜底且乱序**（v15→v16）：
   - v15 症状：`TOC_API_CODE-1`（API 拒绝）→ 走 direList 兜底 → 只有 120 章且"最新章节在最前"。
   - **根因：AES 密钥每日轮换**。HAR 里浏览器密文解密验证了算法（Python 加密逐字节一致），
     对比动态 JS 文件名发现已换（旧 `xhzaj...` → 新 `IdE1A7zo...`）。换新密钥 API 立即 `code:0`。
   - 修复：动态提取密钥/IV + 分页按 URL 去重 + 兜底按章号排序 + API 部分失败也合并兜底。
6. **validator toc 阶段误报 CAPTCHA**（v16 验证期）：
   - 症状：detail 成功、toc 报 `CAPTCHA_DETECTED`，但响应体是正常详情页。
   - 根因：validator 执行规则前扫描页面，命中纠错举报表单 `<div class="captcha">`；
     **决定性证据**：换成纯静态 toc 规则（不访问任何页面）仍报 CAPTCHA → 拦截在规则执行前。
   - 处置：改用**真 Rhino 规则级验证台**（本技能 `scripts/rhino_harness.js`），287/689 章两本书实测通过。
7. **搜索失效：signJs v17 指纹升级**（v17，2026-10-14）：
   - 症状：搜索抛 `ReferenceError: "navigator" 未定义`（AnalyzeUrl.evalJS 阶段）。
   - 根因：rrssk 升级签名 JS（`?action=signJs&v=17-20261014`），新增 3 项指纹且总分改**恰好 31 分**制：
     `navigator.userAgent`(+2)、`createElementNS`(+4)、`documentElement.contains`(+2)；
     另有 `isTrusted` 事件检查（fakeWin 同步回调 `{isTrusted:true}` 已满足）。
   - 修复：Mock DOM 补 3 项 + eval 签名时 navigator 作为第 3 参数传入。**只改搜索，目录/正文未动**。
   - 验证：真 Rhino 端到端——签名非零、搜索 **20 本书**（TOP3: 斗破：狐族公主/混沌天帝/魂殿顾炎）、目录回归 287 章 ✓。
   - 教训：**Mock DOM 是指纹军备竞赛**——签名站会不定期增补指纹项；症状是 ReferenceError 或签名 `00000000`，
     按"抓最新 signJs → 逐项补 Mock DOM → 检查计分制 → Rhino 端到端复测"流程处理。

## 可复用要点（其他 rrssk 合作站/签名站通用）

1. **搜索三步链模板**：00PB → signJs（Mock DOM 执行）→ POST → q token 拼 URL。
2. **两段式属性规则**：任何 `onclick`/`data-*` 藏 URL 的站，用 `属性名\n@js:`。
3. **动态密钥提取模板**：随机名 JS 正则 → 抓取 → `new AESCrypt\('...'\)` + `Utf8.parse\('...'\)`。
4. **分页去重 + 兜底排序**：API 分页假设重叠，按主键去重；兜底目录从 URL 提章号排序。
5. **validator 误报识别**：detail 过而 toc 报 captcha + 纯静态规则复测仍报 → 误报，用 Rhino 验证台。
6. **签名站指纹升级应对**：ReferenceError/`00000000` → 抓最新 signJs 通读 → 补 Mock DOM（含 navigator 参数传入）→ 检查"恰好 N 分"制 → Rhino 端到端复测；只改搜索不动其它链路。
